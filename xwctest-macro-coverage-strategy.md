# Strategy: restoring logMap/logMeta coverage via a shared XWCTEST_IF_ macro generator

## Context

A recent merge of `origin/dev` (real hardening work: corruption-resync logic in `logMap`, new
`DEBUG_CRUMB` tracing) into the coverage-focused branch dropped or bypassed some fault-injection
test hooks in `libMagAOX/logger/logMap.hpp`/`logMap.cpp`, and `libMagAOX/logger/logMeta.hpp`/
`logMeta.cpp` never had any hooks to begin with. Verified current state (via de-duplicated
per-line gcov, not raw multi-namespace-copy percentages, which are misleading for
`logMap.hpp` since it's compiled once per `XWCTEST_*` fault variant):

| File | Coverage | Real gaps |
|---|---|---|
| `libMagAOX/logger/logMap.cpp` | 100% | none |
| `libMagAOX/logger/logMap.hpp` | 98.27% | 5 lines (1 already `LCOV_EXCL`'d) |
| `libMagAOX/logger/logMeta.cpp` | 91.49% | 33 lines (18 already excluded) |
| `libMagAOX/logger/logMeta.hpp` | 47.69% | 136 lines — zero existing hooks |

Separately, a prototype at `./tbd/` (`genTestMacros.py`, `appDevTestMacroTemplate.jinja2`,
`testMacros.hpp`) sketches a pattern for minimizing how much test-only scaffolding lives in
production source: instead of a raw

```cpp
// clang-format off
#ifdef XWCTEST_SOMENAME
    someStatement(); // LCOV_EXCL_LINE
#endif
// clang-format on
```

block (4-5 lines) at every fault-injection site, a generated header defines one macro per test
name:

```cpp
#undef XWCTEST_IF_SOMENAME
#ifdef XWCTEST_SOMENAME
#define XWCTEST_IF_SOMENAME(line) \
(line); /* LCOV_EXCL_LINE */
#else
#define XWCTEST_IF_SOMENAME(line) do {} while(0)
#endif
```

so production code shrinks the site to one line: `XWCTEST_IF_SOMENAME( someStatement() );`. This
pattern is currently unused anywhere in the repo — `./tbd` is a pure design sketch, not wired
into any build. A repo-wide survey found ~139 genuine single-fault-site `#ifdef XWCTEST_*` blocks
across 15 production files (most are single-statement, good conversion candidates; a minority are
multi-statement blocks, macro-of-macros, or default-value overrides that don't fit the "wrap one
line" shape and must stay raw), plus ~30 separate `XWCTEST_NAMESPACE` double-include occurrences
(a different mechanism — recompiling a whole templated class under a test namespace — which this
pattern does not replace and which stays exactly as-is).

## Decision: one shared generator, not one per test directory

Rather than copying `genTestMacros.py` + its template into each adopting test directory, promote
a single shared generator (so future adopters — `stdCamera.hpp`, `MagAOXApp.hpp`, `stdSubDir.hpp`,
etc., all found to have similar convertible sites — don't duplicate the script):

- Promote `./tbd/genTestMacros.py` and `./tbd/appDevTestMacroTemplate.jinja2` to `tests/`
  (generalizing the template's filename and its hardcoded "generated by
  libMagAOX/app/dev/tests/genTestMacros.py" header comment, since it's no longer directory-specific).
- Wire up the script's already-imported-but-unused `getopt` to accept `--names <file>` and
  `--out <path>`, replacing the hardcoded `gXwcTests` list and hardcoded output path.
- Each adopting directory keeps its own plain names file (e.g.
  `libMagAOX/logger/tests/xwcTestNames.txt`, one `XWCTEST_NAME` per line, `XWCTEST_` prefix
  stripped the same way the original script already does: `x[(x.find("_")+1):]`) and generates its
  own local `testMacros.hpp` by invoking the shared script with its own `--names`/`--out`.
- Remove `./tbd` once its logic is promoted — nothing references it today, so it's dead weight
  once superseded.

Production headers include their directory's generated macro header, e.g. from
`libMagAOX/logger/logMap.hpp`: `#include "tests/testMacros.hpp"`. This is an intentionally unusual
dependency direction (production including something that lives under `tests/`), but it's safe:
every macro no-ops (`do {} while(0)`) unless a specific test translation unit `#define`s the
corresponding `XWCTEST_*` name before including the header — production builds never do.

## Logger adoption

`libMagAOX/logger/tests/xwcTestNames.txt` will list, at minimum, the 13 existing `logMap.hpp`
hooks and 1 existing `logMap.cpp` hook (straight 1:1 renames — e.g. `XWCTEST_LOGMAP_AFLTFM_XWCE`
becomes callable as `XWCTEST_IF_LOGMAP_AFLTFM_XWCE(line)`), plus any new hooks needed to close the
5 real `logMap.hpp` gaps (lines 156, 816, 842-843, 932 in the current merged file — see the
uncovered-line detail in the investigation notes below). Real test data will be tried first for
each; a new macro will only be added where that proves impractical. The clearest candidate for a
new hook is `getNextLog`'s resync-failure branch (line ~932) — existing test attempts to reach it
spuriously succeed at resync instead of failing, so a hook that forces `logMapResync()` to return
`nullptr` deterministically is likely the most reliable route.

Existing `logMap.hpp`/`logMap.cpp` conversions:
- Add `#include "tests/testMacros.hpp"`.
- Replace each raw `#ifdef XWCTEST_LOGMAP_*` / `#ifdef XWCTEST_LOGINMEMORY_*` block with a single
  `XWCTEST_IF_*(statement);` call.
- Decide the fate of 3 dormant, currently-unused hooks left over from the merge
  (`XWCTEST_LOGMAP_LATFM_BADALL4/5/6` — each guards a single `throw`, never invoked by any test):
  either wire them into new test `SECTION`s (mirroring how `BADALL1/2/3` are already driven) or
  remove them as merge cruft. No coverage impact either way today (they're non-executable in every
  current build variant), but leaving unused scaffolding around is confusing.

`logMeta.hpp`/`logMeta.cpp` have no existing hooks at all, and most of their gaps don't need any —
they're reachable through direct test calls and crafted failure data, not fault injection:
- `logMetaGapReason()`, `reportUnverifiableLogEntry()`, `getPriorVerifiedLog`/`getNextVerifiedLog`
  are free functions/templates, callable directly from new `TEST_CASE`s with hand-built buffers
  (some entries valid, some with corrupted flatbuffer payloads that fail `verifyLogEntry`).
- `unavailableReason()`/`unavailableCard()` just need a direct call in a small new `TEST_CASE`.
- The ~29 per-value-type failure branches in `valueNumber()`'s State/Continuous switches (only the
  `Char` case is currently exercised) are reachable by querying each value type against an
  empty/no-data `logMap`, which naturally makes the underlying `getLogStateVal`/`getLogContVal`
  return nonzero — no macro needed.
- A new `XWCTEST_IF_*` hook (via the same generator, added to logger's names file) is added only if
  a specific branch proves genuinely unreachable through data alone after attempting the above.
